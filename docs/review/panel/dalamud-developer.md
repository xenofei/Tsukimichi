# V3 proposal review: Dalamud plugin developer

Date: 2026-09-28. Reviewed: docs/feature-plan-v3.md, docs/review/bug-hunt-0.5.0-core.md, docs/review/bug-hunt-0.5.0-ui.md, docs/data/verification-report-2.md, docs/design/ui-revamp-proposal.md §6, docs/design/glyphs/imgui-notes.md, and the code named below. Every API claim was checked against the installed Dalamud (API 15, `%AppData%\XIVLauncher\addon\Hooks\dev`, 2026-09-17 build): the XML docs, and the assemblies themselves by reflection where the XML lists only documented members (FFXIVClientStructs field layouts, Dalamud.Bindings.ImGui enum values and method overloads, Lumina.Excel sheet types). Nothing in the repo was edited.

Verdict in one paragraph: the plan is technically sound and most of its hedges are unnecessary; the two client structs it is unsure about exist and are cheap to read. The real risks are elsewhere: the daily-offer fix is right but the "accepted daily" companion has one subtle trap; the snapshot schema bump in T3 combines with `JsonSnapshotStore`'s quarantine-on-unreadable behaviour to make a downgrade destructive; the ImGui binding Dalamud ships has no shortcut API, so T17's keyboard work is hand-rolled; P13 cannot reuse the item-hint hook pattern at all; and 0.6.0 as scoped bundles evaluator semantics, data-model changes, a schema bump and a multi-hour scraping task into one release. The official-repository item that nobody on the panel has raised is the AI usage policy: the plan's execution model ("one implementer agent per task") must be disclosed on submission, and an entirely agent-written plugin is rejected outright.

## 1. Feasibility and risk, task by task

### T3 Missing requirement kinds (satisfaction rank, carrier level, festival phase)

The structs exist. Verified by reflection on the installed FFXIVClientStructs.dll:

| Need | Where it is | Notes |
|---|---|---|
| Custom delivery satisfaction rank | `FFXIVClientStructs.FFXIV.Client.Game.SatisfactionSupplyManager.Instance()`; `SatisfactionRanks` (`Span<byte>`, 12 slots at 0x1A), `Satisfaction` (`Span<ushort>`, 12 slots at 0x2), `UsedAllowances` (12 bytes at 0x26), plus `GetUsedAllowances()`, `GetRemainingAllowances()`, `GetResetDateTime()` | 12 slots = one per `SatisfactionNpc` row (rows 1..12; row 0 is empty), so the index is `SatisfactionNpc.RowId - 1`. That mapping is the one thing to confirm in game (talk to M'naago, `SatisfactionNpc` row 2, and check `SatisfactionRanks[1]`). A 13th delivery NPC in a later patch overflows the fixed array until ClientStructs updates; guard with `RowId - 1 < SatisfactionRanks.Length` and report "not checked" past the end. |
| Delivery Moogle carrier level | `PlayerState.DeliveryLevel` (byte at 0x5FD, doc: "Carrier Level of Delivery Moogle Quests"), and Dalamud already surfaces it as `IPlayerState.DeliveryLevel` | No unsafe code needed; `GameStateReader` already holds an `IPlayerState`. `Quest.DeliveryQuest.RowId` equals the carrier level on every row (verification-report-2 §2 row 3). |
| Festival phase | `GameMain.Festival { ushort Id; ushort Phase }`, `GameMain.ActiveFestivals` is **8** slots (not 4; the "array of 4" remark in the XML is for `LayoutWorld.LoadPrefetchLayout`). Two more copies exist: `PlayerState.ActiveFestivalIds` / `ActiveFestivalPhases` (8 each, at 0x168/0x178) and `EventFramework._festivals` (8). `ZoneInitPacket` carries separate `GameFestivalIds/Phases` and `UiFestivalIds/Phases`. | The plan reads `GameMain`. Nobody has established which of the three arrays the quest system consults, nor whether `GameMain`'s is cleared during a zone load (bug-hunt P3). Log all three for one event before choosing; my expectation is that `PlayerState`'s pair is the server-sent per-character state and the most stable, with `GameMain` following the layout. |

So the plan's hedge "if ClientStructs exposes it, otherwise 'not checked'" should be replaced by a hedge on the index mapping only. Effort M is right. Two follow-ups the task text does not list:

- `SnapshotDiff.Compute` (Tsukimichi.Core/Runtime/SnapshotDiff.cs:52-53) diffs `ActiveFestivals` as a set of ids. Once phases are stored, a phase change with the same id must also count as a changed festival, or a phased event never re-resolves mid-session. `OtherInputsChanged` (:63-75) must also compare the new satisfaction ranks and carrier level, or those quests stay stale until some other input moves.
- `StateResolver` rule 3 (StateResolver.cs:157-161) keys on `s.ActiveFestivals.Contains(q.Festival)` independently of the requirement list; the phase window has to be applied there as well as in `RequirementEvaluator`, or the state and the requirement line disagree.

Bonus, same area: `PlayerState.MaxLevel` (byte at 0x79) and `PlayerState.MaxExpansion` (byte at 0x7A, "Row Id of ExVersion sheet") exist, so the "DRAFT-NEEDED E" hedge at GameStateReader.cs:232-233 can be closed in the same task. Semantics for a free-trial or un-entitled account need one in-game check; keep 0 = unknown as the fallback.

### T5 Core/Game bug fixes

- **Daily offer (C1).** Confirmed from the struct: `QuestManager._dailyQuests` is `FixedSizeArray12<DailyQuestWork>` and `DailyQuestWork` has exactly `QuestId` (ushort) and `Flags` (byte) plus `IsCompleted`; it is the accepted-dailies work array, not an offer. The game does not store the day's offer anywhere readable: it is computed per NPC from `QuestManager.DailyQuestSeed` (byte at 0x6D8) by `DailyQuestMap.CalculateAvailableQuests(Character*, Node* iterator, byte seed, bool rankInRange, byte rank, bool rankExactMatch, QuestEventHandler** outResult)` on `EventFramework.DailyQuests`. Do not call it: it needs a questgiver iterator into an `StdMap` and writes through an event-handler pointer. Dropping the offer requirement is the correct fix.
- **Accepted dailies (C2).** `DailyQuestWork` has no `Sequence`, so the plan's "use 0" is fine. Trap: a daily that was turned in today still sits in the array with the completed flag; the plan says "non-completed entries", which is right, but note that `QuestManager.IsQuestAccepted(ushort)` exists and might be a cleaner source of truth for "in the journal" than scanning both arrays. Either way the resolver's rule 4 should run before rule 5 for dailies (accepted beats done-this-cycle).
- **Parent-job class quests (P2 plausible).** `QuestWork.AcceptClassJob` (byte at 0x12) records the job a journal quest was accepted on. That is direct evidence for the in-game check the plan defers: if a Dragoon's journal shows a Lancer quest with `AcceptClassJob == DRG`, the game admits the parent. Read it into `AcceptedQuest` while you are in that code.
- **Festival context (C3/G1).** `SessionState.SetCatalog` (SessionState.cs:216) is the right place. `curated/festivals.json` is empty, so `WithFestivalEnds` does nothing until it is populated; the plan's tests should include the empty-file case.
- **Character switch (G3).** Fix location is right (SessionState.SetLive; StatePoller.cs:246-258).
- **Perf (C8).** Trivial. While there: `StatePoller.Poll` (StatePoller.cs:219) allocates a `HashSet<ushort>` in `ReadDailyOffer` every 1 s poll; it disappears with the offer requirement.

One thing neither bug hunt covers: after `RetryCatalogAsync` (Plugin.cs:74-99) installs a new `CatalogBundle`, `StatePoller.Poll` keeps `last` and `states` from the old bundle and returns null on an empty diff, so live states are not re-resolved against the new catalog until something else changes. Verify whether the poller resets on `SessionState.Changed`/bundle identity; if not, T5 should reset `last` when `session.Bundle` is a new instance.

### T6 / T11 / T14 ImGui tree rows, custom tab strip, whole-window chrome

Binding facts (Dalamud.Bindings.ImGui, reflected):

- `ImGuiTreeNodeFlags` = None, Selected, Framed, AllowItemOverlap, NoTreePushOnOpen, NoAutoOpenOnLog, CollapsingHeader, DefaultOpen, OpenOnDoubleClick, OpenOnArrow, Leaf, Bullet, **FramePadding**, SpanAvailWidth, SpanFullWidth, NavLeftJumpsBackHere. So T11's `FramePadding` + pushed `ImGuiStyleVar.FramePadding` approach works, and `GetItemRectMin/Max` then covers the padded frame, which is what `DrawNodeOverlay` (TreePane.cs:110-152) centres on. Keep `SpanAvailWidth`; do not add `SpanFullWidth` on top (they change the hit rect differently).
- `ImGui.TableSetBgColor(ImGuiTableBgTarget, uint[, int])` exists with targets RowBg0/RowBg1/CellBg, so T15's fills through the clipper are fine. Caveat for the "hover lift": `TableGetHoveredRow` is an imgui_internal function and is not bound, so hover must be painted from the previous frame's `IsItemHovered` (one-frame lag) or drawn on the draw list after the `Selectable` instead of via `TableSetBgColor`.
- This is an ImGui 1.8x-era binding: there is **no** `ImGui.Shortcut`, `SetNextItemShortcut`, `IsKeyChordPressed` or `SetItemKeyOwner`. See T17.
- `ImDrawListPtr.PathArcTo(center, r, a0, a1, segments)`, `PathStroke(col, ImDrawFlags, thickness)`, `AddImageRounded(tex, min, max, uv0, uv1, col, rounding, flags)` all exist with the overloads imgui-notes.md and §6.1 assume. `ImDrawFlags` has no round-cap flag, so the two cap discs in `DrawHalo` are the right workaround.
- `ImGuiIOPtr.KeyShift/KeyCtrl/KeyAlt/KeyMods` exist for T7.

Whole-window Night chrome: `Window.PreDraw()` and `PostDraw()` are virtual on `Dalamud.Interface.Windowing.Window` (also `PreOpenCheck`, `DrawConditions`, `BgAlpha`, `TitleBarButtons`). Push `ImGuiCol.WindowBg/TitleBg/TitleBgActive/TitleBgCollapsed/Border/ScrollbarBg/...` in `PreDraw`, pop in `PostDraw`; `WindowSystem` calls them around `Begin/End`. Two consequences the revamp proposal gets backwards (§6.3 "popups / config keep the host style"): a colour pushed before `Begin` is still on the stack while `Draw` runs, so every popup, combo, tooltip and child begun inside `Draw` inherits it; if popups are meant to keep the host style, `Theme.PushNightWindow` must be popped around them explicitly (or pushed only around `DrawContent` as the plan text says, which then does not tint the title bar). Decide which, and note Dalamud's own title-bar buttons (pin, click-through) render in whatever `TitleBg` you push. Also keep `BgAlpha` untouched, or the user's Dalamud "window opacity" stops working on this window; that is the kind of thing a reviewer clicks.

Custom tab strip vs the tutorial: `TutorialOverlay.cs:81` targets the literal key `"tabs"`, recorded once at MainWindow.cs:679 from the cursor position after `BeginTabBar`. A `TabStrip` must record the union of its buttons under `UiRects.Tabs`; that is the whole contract, and the tutorial's `TryUnion` (TutorialOverlay.cs:275-296) tolerates any rectangle. The layout risk is different: `DrawNavigation` draws the tabs inside the `##left` child whose column is `UiMetrics.LeftColumnWidth = Px(240)` (UiMetrics.cs:78). A vertical rail inside that column takes ~44 px from a 240 px tree, and MW-1 (minimum size ignores UiScale) already collapses the centre column at 1.5×. Put the rail in its own fixed column of the `##layout` table (MainWindow.cs:616-621) and fix MW-1 first (T6 lists it).

Keyboard navigation claim in T11 ("preserved by keeping TreeNodeEx under the overlay") holds; the hidden-label trick (TreePane.cs:83) already does this.

### T17 Motion, typography, secondary panes

- Fonts: `IUiBuilder.FontAtlas` (plugin-private atlas) and `IFontAtlas.NewGameFontHandle(GameFontStyle)` exist; `GameFontFamilyAndSize` has Axis96/12/14/18/36 (and Jupiter, Meidinger, MiedingerMid, TrumpGothic). `IFontHandle.Push()` returns `IDisposable`, `Available` says whether it is built, `ImFontChanged` fires on rebuild, and the docs state the handle must be created **outside** `BuildStepChange` handlers and once (creating a second one without disposing the first throws). Real caveats the plan does not mention: (1) the game fonts are pre-baked bitmap fonts at fixed sizes; `UiMetrics.ApplyFontScale` calls `ImGui.SetWindowFontScale(FontScale)` (UiMetrics.cs:45), which scales the bitmaps bilinearly, so Axis14 at UiScale 1.15/1.6 is blurrier than Dalamud's default vector font at the same size; pick the family-and-size nearest to `FontDefaultSizePx × FontScale` per scale bucket instead of scaling one handle. (2) The first `Push` of an unbuilt handle triggers an atlas build (a visible hitch of ~100 ms and a new texture page); build it on plugin load via `BuildFontsAsync` and gate with `Available`. (3) `IsGlobalScaled` on the atlas decides whether Dalamud's global scale slider rebuilds the font; leave the default. The §6.3 plan of shipping the `AddText(font, size·0.85)` fallback first and handles later is correct; I would go further and keep the fallback permanently for captions, using a handle only for the display size.
- Keyboard shortcuts (Ctrl+F, Ctrl+1..4, F, Enter): with no `Shortcut` API, the implementation is `ImGui.IsWindowFocused(ImGuiFocusedFlags.RootAndChildWindows) && !ImGui.GetIO().WantTextInput && io.KeyCtrl && ImGui.IsKeyPressed(ImGuiKey.F, false)`; the `WantTextInput`/`IsAnyItemActive` guard matters because the search box is an `InputText` and "F" alone is a plain letter. Don't consume Ctrl+1..4 while the game chat has focus; the window-focus check already does that.
- `Motion` on `ImGui.GetTime()`: fine; `GetTime` exists.

### T9 / T10 / T12 / T13 / T15 / T16

All of these are draw-list work on APIs verified above. Two notes:

- T15 Cards mode with banner thumbnails via `TryGetWrap`: `ITextureProvider.GetFromGameIcon(...).TryGetWrap` is what DetailPane.cs:300 already does. The cost is not draw calls but texture churn: quest banners are large icons, and scrolling a 5k-row table in Cards mode requests a new set per clipper page; Dalamud's texture cache evicts unused wraps after a short idle, so memory stays bounded, but the first frames of every scroll stop show placeholders. Acceptable as an opt-in mode (decision 5 says it may slip); do not make it the default density.
- T13 `ImageCover` centre-crop UVs and `Scrim` gradients: `AddRectFilledMultiColor` (used at DetailPane.cs:319) and `AddImageRounded` exist; no issue.

### P2 "Why not offered?" via IContextMenu

`MenuTargetDefault` exposes `TargetName`, `TargetObjectId` (ulong), `TargetObject` (`IGameObject?`), `TargetContentId`, `TargetHomeWorld`, `TargetCharacter` (`CharacterData?`, "only shows up for specific targets like friends, party finder listings"). `IGameObject` has `ObjectKind`, `BaseId` (the ENpcResident row for an EventNpc) and `DataId`. So the filter is `args.MenuType == ContextMenuType.Default && args.Target is MenuTargetDefault { TargetObject: { ObjectKind: ObjectKind.EventNpc, BaseId: > 0 } npc }`, exactly mirroring DiscoveryCommands.Which (DiscoveryCommands.cs:63-69). Where the menu comes from: an NPC in the world does not open a context menu on right-click (that interacts); the Default menu for an NPC target opens from the target bar / target name (AgentContext), and that path does fire `IContextMenu.OnMenuOpened`. `TargetObject` can be null when the object id is not in the object table at that instant; fall back to `ITargetManager.Target` if `TargetObjectId` matches, otherwise add nothing. Filtering to `EventNpc` also keeps the entry off player menus, which matters for the data-collection rule (§2). The `(N)` count must be computed synchronously in the handler; `QuestDiscovery.IssuedBy` is a catalog scan, which is fine at 5k rows. `/tsuki why <quest>` is a name lookup through `SearchIndex` (MainWindow.cs:250-257 shows the pattern). Effort S is fair.

### P13 Duty Finder unlock hint

The plan's "same hook pattern as the item hover hint" does not transfer: `HoverHint` (HoverHint.cs:96) relies on `IGameGui.HoveredItem`, and there is no hovered-duty equivalent. What exists:

- `AgentContentsFinder.Instance()` with `SelectedDuty` (`ContentsId`, at 0x1EC8), `SelectedContent` (`StdVector`), `ContentList` (`StdVector`), `SelectedTab`, `HasRouletteSelected`, `ListChanged/DetailsChanged` flags, and `OpenRegularDuty(uint cfc, bool)`. The addon `AddonContentsFinder` has `DutyList` (`AtkComponentTreeList*`), `SelectedRow` (uint at 0x18FC), `SelectedDutyTextNode[5]`.
- `IAddonLifecycle.RegisterListener(AddonEvent.PostRefresh | PostReceiveEvent | PostUpdate, "ContentsFinder", handler)`; `AddonReceiveEventArgs` carries `AtkEventType`, `EventParam`, `AtkEvent`, `AtkEventData`. `IAddonEventManager.AddEvent(addon, node, AddonEventType.ListItemRollOver / ListItemRollOut / ListItemClick, handler)` exists for node-level hover, but tree-list rows are recycled nodes, so mapping a hovered row back to a `ContentFinderCondition` id means indexing `ContentList` by the row's list index, which breaks whenever the list is filtered or collapsed.

Recommended shape: hint on **selection**, not hover. On `PostReceiveEvent`/`PostRefresh` of `ContentsFinder`, read `AgentContentsFinder.Instance()->SelectedDuty`, resolve its CFC → `InstanceContent` the way RewardUnlockReader.cs:191-193 already does (`UIState.IsInstanceContentUnlocked(instance)`), and if locked, draw the Tsukimichi panel beside the addon (placement code from HoverHint.DrawWindow/`TooltipRect` reused with addon name "ContentsFinder"). Verify in game that a locked row can be selected and that `SelectedDuty` populates for it; if the game refuses selection on locked rows, fall back to `ListItemRollOver` on `DutyList` and accept the index mapping. "Raid Finder" is the same addon on another tab. Effort M is right only with the selection design; hover-accurate is L.

### P9 Journal text reader

- Sheet access: there is **no** `QuestDialogueText` type in the shipped Lumina.Excel 7.x (reflected: none of the 90+ `Lumina.Excel.Sheets.Quest*` types is it). Two working routes: `IDataManager.Excel.GetRawSheet("quest/000/ManSea001_00039", language)` and read `RawRow.ReadStringColumn(1)` with the key in column 0; or declare your own `[Sheet]` row (`SheetAttribute(string name, uint columnHash)`; the column hash is optional) and call `IDataManager.GetExcelSheet<T>(language, name)`, whose doc says "Explicit names are necessary for quest/dungeon/cutscene sheets". Path is `quest/{first three digits of the five-digit number}/{Quest.Id}` (`QuestRecord.InternalId` is already mapped, CatalogMapper.cs:16). The journal entries are the keys with the quest's sequence markers; verify the exact key pattern against one sheet dump from DataGen before designing the model, and treat missing files as "no text" (retired rows have no sheet).
- Text is SeString: player name, gender forks (`<If(PlayerParameter...)>`) and RSV strings appear in dialogue and some journal lines. Extract through Lumina's `ReadOnlySeString` and Dalamud's SeString evaluator so forks resolve for the current character; a raw `ExtractText()` leaves markup in the reader.
- Size and memory: ~5.4k small `.exh/.exd` pairs (a few KB to ~100 KB each), on the order of 100 MB of English text in total. Per-quest lazy loading is cheap (one file, on the framework thread or off it: Lumina reads are thread-safe, which LuminaCatalogLoader.cs:15 already relies on). Full-text search is the problem: `ExcelModule` caches every sheet it opens for the lifetime of the `GameData` instance (there is `UnloadTypedCache(Assembly)` for typed sheets, nothing for raw ones), so indexing all quests through `IDataManager.Excel` retains them all. Build the index in a background task, write it to the config directory keyed by the game version stamp, and read the sheets through `IDataManager.GetFile<ExcelDataFile>` (no module cache) rather than `GetRawSheet`; measure resident memory before and after on the first run. Keep "opt-in, lazy" exactly as the plan says.
- Rules: showing text the client shows is fine; keep "Copy entry" to the clipboard and do not add a bulk text export (that starts to look like redistribution of game text).

### P12 Export

Feasible and rule-safe as long as it is a file write with no upload. Write into `IDalamudPluginInterface.GetPluginConfigDirectory()` or offer a save dialog (`Dalamud.Interface.ImGuiFileDialog.FileDialogManager`); print the path to chat. Include only the viewed character; the own-account content id is fine (own characters), but xiv-shinies and FFXIV Collect key on Lodestone character ids, which the plugin cannot know, so the format should carry name + world and let the importer resolve. "Moonlit obtained state" is live-only (`RewardUnlockReader` reads `UIState`), so the export for a stored character is quest completion only; say so in the UI.

### P8 Patch of origin

The seed source is the weak point. consolegameswiki text is CC BY-NC-SA 3.0; a quest→patch fact table is not copyrightable, but bulk-scraping their per-patch pages into a shipped file invites both a licence argument and a ToS one. Prefer: (a) derive from sheet data where possible (the `QuestChapter`/`QuestRedoChapterUI` sheets carry patch chapters for MSQ; row-id ranges are monotonic per patch for most genres), (b) seed the remainder once from Garland's quest index (which already carries a patch field and is the source verification-report-2 uses), (c) commit `docs/data/quest-added-in.csv` with a provenance column and maintain it forward by diffing DataGen runs (`--diff-previous <unique_quests.json>` emitting new row ids, stamped with the current game version → patch through a 20-line lookup table). The plugin ships only the id→patch map.

### T2a Full-catalog verification

Feasible but it is a scraping job, not plugin work: ~5.4k Garland documents, ~5.1k Lodestone pages plus search pages, wiki raw pages for disagreements, FFXIV Collect dumps. At the polite 1 request/s the plan implies, that is 4–5 hours of wall time; make it resumable, cache raw responses on disk outside the repo, commit only the CSVs. Lodestone returns 429 under load and needs a UA. See §4 for where this code should live.

### T1 Unlisted refiling

Rules are deterministic and the counts are pinned by tests; fine. Two fragilities: rule 1 keys on `Unknown12`, a Lumina.Excel auto-named column that is renumbered whenever EXDSchema changes (CatalogMapper.cs:140 already depends on `QuestAcceptAdditionCondition.Unknown0` the same way); pin it with a data test that fails loudly on a Lumina bump. And "retired never counted" has more consumers than TreeCounts: `SearchAndPrint` (MainWindow.cs:250-258), the Wotsit registration of every catalog quest (WotsitIpc), `HoverHint`/`ItemHooks` lookups for unique rewards whose quest is retired, `MsqProgress`, `FeaturePresets.Derive`, Compare-with, and the DTR/Nearby counts. Put `IsRetired` in one place (`QuestCatalog.Listed` or a filtered `All`) rather than at every call site.

### T2 / T4 / T7 / T8

No API concerns. T7: `io.KeyShift` exists; disable the button and show "Hold Shift and click" as planned. T4: pick explicit item ids for `online_store.json`, not the "past-year festival collectibles" rule; the rule cannot be verified and the ids can.

## 2. Official-repository rules a reviewer would raise

Sources checked today: DalamudPluginsD17 README, dalamud.dev/plugin-publishing/restrictions, the XIVLauncher Acceptable Use Policy.

1. **AI usage policy (new, and the most important item for V2-20).** The D17 README: "If you used AI tooling at any point, review the AI Usage Policy and disclose your level of AI use in the PR description", and "Entirely AI-generated submissions will be rejected, and undisclosed AI use may result in a ban." The plan's execution method is "one implementer agent per task in an isolated worktree, coordinator merges, bug-hunter review". If V2-20 is still a goal, the owner needs to be able to describe their own authorship and review of the code honestly, and the submission must disclose the agent workflow. Decide this before 0.9.0, not at submission time.
2. **Automation.** "Your plugin does not interact with the game servers in a way that is automatic, as in polling data or making requests without direct interaction from the user." Nothing in the plan does; P2 and P13 are informational, `/tsuki why` prints text. Keep it that way: no "accept quest" or "open duty" buttons (`AgentContentsFinder.OpenRegularDuty` exists; do not call it).
3. **Data collection.** "Your plugin does not collect account IDs of player characters beyond your own in any form." Compare-with stores the owner's own characters, fine. P2 must never persist `MenuTargetDefault.TargetContentId`; the EventNpc filter avoids player menus entirely.
4. **Monetization.** "Your plugin does not interfere with Square Enix's monetary interests (i.e. granting access to Mog Station items)." T4's "also on the Online Store" label is information, not access; fine. Do not add store deep links.
5. **Combat/PvP.** Not applicable.
6. **Network.** The plugin makes no network calls (only DataGen has an `HttpClient`, XivApi.cs:19). Keep P11's "end dates as static data" and P12's file export; a reviewer greps for `HttpClient` in the plugin project.
7. **Licensing.** No LICENSE file exists in the repo today (checked). D17 does not mandate a specific licence, but the repository must be public and buildable by their CI from `manifest.toml` (`repository`, `commit`, `owners`, `project_path`), and the plugin must build with the current `Dalamud.NET.Sdk` (it does: `Dalamud.NET.Sdk/15.0.0`). Decision 7 (MIT vs AGPL) is a preference; MIT is what most listed plugins use. Third-party data: curated `note` fields and P5's spoiler-free descriptions must be original wording, not wiki sentences (CC BY-NC-SA); id lists derived from FFXIV Collect are facts and fine, but say where they came from in `curated/README.md`.
8. **Manifest/technical.** Icon must be a PNG between 64×64 and 512×512 (check `assets/icon.png`); "version and assembly version must not be based on a timestamp"; new plugins go to `testing/live` first. `DownloadLinkInstall` in pluginmaster.json is irrelevant for D17 (they build it).
9. **Naming.** "Tsukimichi" has no collision I know of in the repository; `InternalName` must stay stable forever once submitted.

## 3. Performance budget at 5k rows

- The table is clipped (`ImGuiListClipper`, TablePane.cs:155-175), so T15's stripe, lift, pills and job icons cost O(visible rows ≈ 30), not O(5k). `TableSetBgColor` per visible row is fine.
- T11 tree: ≤ ~60 nodes × ≈ 9 primitives for a partial halo ≈ 540 draw calls in one list, no texture switches; negligible. Cap arc segments as imgui-notes.md says.
- `Motion` keyed by RowId with 2 s pruning is fine as long as only visible rows touch it (§6.3 says so). Do not key hover on the row index.
- The frame-time risks are not in drawing: (a) `QueryRunner` re-runs the whole query on any filter change (already true today; U7/U8 show where whole-catalog recomputes hide); T1's provenance strings and T2's display level must be materialized at catalog build, not per draw; (b) T3/T5 make `ResolveAll` fire on festival phase and satisfaction changes; the incremental `ResolveDependents` path exists (StatePoller.cs:289-291) and should be kept for those inputs; (c) P9's full-text index is the only thing that can hitch the game and must be off-thread; (d) Cards mode texture churn (above).
- 5k `MoonGlyph` calls never happen in one frame anywhere in the plan; the only unclipped list I found is the tree, which is small.

## 4. Release engineering

- **0.6.0 is too large and mixes kinds of risk.** T1 (data model + tree semantics + count changes everywhere), T3 (new requirement kinds + snapshot schema v2), T5 (evaluator semantics), T2a (a multi-hour scraping tool whose findings feed T2–T4), T6 (a dozen unrelated UI fixes), T7, T8. If a user reports "my totals changed" after 0.6.0, four of those tasks are suspects. Split: **0.6.0** = T5 + T6 + T7 + T8 + T2 + T4 (bug fixes, guards, level display, curated corrections; additive schema only). **0.6.1 or 0.7.0-pre** = T1 + T3 (model and schema changes, with their own changelog and a week of the owner's play). T2a runs in parallel as a tool and its corrections ship as data-only patch releases (`unique_quests.json` and curated files change, code does not).
- **T2a belongs in a separate tool, not DataGen `--verify --all`.** DataGen is the reproducible generator reviewers read and the release pipeline may run; a Lodestone/Garland/wiki scraper with an on-disk cache, rate limiting and resumability is a different program with different failure modes. Make it `tools/Tsukimichi.Verify` (console, references Tsukimichi.GameData for the catalog, no plugin dependency), keep DataGen's existing xivapi sample check as the fast gate. It also keeps `HttpClient` out of anything that could be mistaken for plugin code.
- **Snapshot schema migration risk is real and in the wrong direction.** `CharacterSnapshot.CurrentSchemaVersion = 1`, the migrator registry is empty (SnapshotMigrator.cs:14), and `JsonSnapshotStore.ReadSnapshot` **quarantines** any file it cannot read (JsonSnapshotStore.cs:130-142), including a file whose version is newer than the build (`Migrate` throws `InvalidDataException`, :40-44). So the moment T3 writes v2, a user who downgrades to 0.5.x (or the owner testing an older build) has every stored character moved aside. Two safer options: (1) keep version 1 and add fields additively (`ActiveFestivalPhases` parallel list or a new `Festivals` list of `{id, phase}` objects alongside the existing `ActiveFestivals`, `SatisfactionRanks`, `CarrierLevel`); System.Text.Json ignores unknown properties on old builds and defaults missing ones on new builds, so nothing needs migrating; (2) if you do bump, make older builds read newer files best-effort instead of quarantining (only quarantine on parse errors). Whichever you choose, Compare-with on a pre-T3 snapshot must render the new requirements as "not checked", which the `MountRequirement` pattern already gives you.
- **Config** is additive (`Density`, `ClassicLayout`, `ReduceMotion`); `Configuration.Version` stays 1. Fine.
- The plan's per-release gates (0 warnings, tests green, bug-hunter pass, changelog, tag → Actions → pluginmaster) are right; add "owner plays one session on the release build with a stored second character" for any release that touches snapshots.
